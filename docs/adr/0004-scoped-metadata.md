# ADR-0004：先绑定单库归属，再引入统一元数据库

状态：接受（T-011，2026-09-23）

## 决定

现阶段继续每工作区一个 SQLite 文件。v9 在请求、Cookie、站点镜像及相关表写入 `workspace_id` / `profile_id`，把正文关联单列为 `body_refs`，且数据库 `meta` 绑定唯一工作区与 profile。存储进程启动时校验绑定；外部操作若明确携带不匹配的范围，返回错误，不回退到活动工作区。`profile_id=primary` 是当前工作区的稳定存储身份；浏览器的 L/H 是运行配置，不拿它表示账号或存储分区。

旧 v8 库只能由默认工作区接收。迁移前使用 SQLite `VACUUM INTO` 留下一致性 `.pre-v9-*.bak`，然后事务内加列、回填、建索引和记录版本/校验和。旧请求的身份来源标 `legacy_unknown`，新请求标 `observed`；不推断登录账号。重复启动核对迁移校验和与库归属。失败时不得返回可写数据库句柄；可关闭程序后用备份文件恢复。

## 边界

这不是多工作区共享一库，也不改变 Chrome Profile 目录。原有 `inst/seq` 继续作为局部引用键；应用层绑定的数据库文件仍是隔离边界。Cookie 的 `partition_key` 沿用浏览器原值，未知值不猜测。现有 `bodies` 哈希去重仍是库内维度。将来合库前必须重建 `(workspace_id, profile_id, inst, seq)` 全局键与 Cookie/站点联合主键，给每个旧文件做冲突检测和可逆导入，并通过双工作区历史读取与故障恢复验收；不能仅把文件拼接。

## 理由

直接合库会把当前按 `inst/seq`、Cookie key、origin 定义的局部主键变成冲突源。先显式归属、强制运行时范围校验，使 T-013/T-014 能在不冒险移动用户资料的条件下开发。
