## 1. 目标与非目标

**目标**：在一个尽量不被页面察觉的浏览器里，把页面看得足够全（请求 / 响应 / body / 脚本 / DOM /
console / 输入轨迹），并且能动手干预（改包、注入、拟人化输入），干预效果由**页面侧**回报。

**非目标**（明确的边界，不是待办）：

- 不做证书固定绕过；代理只为补时序与改写大 body
- 不做多机 / 云端采集，单机单实例
- 不承诺二进制级无痕。Profile H 只是「不开高风险 CDP domain」，真正的内核改造是 P4/P7

## 2. 总体架构

### 2.1 进程模型

六个进程，主进程只做编排，**重 IO 与网络面一律不在主进程**：

| 进程 | 入口 | 职责 | 与主进程的通道 |
| --- | --- | --- | --- |
| Electron 主进程 | `src/main/index.ts` | 编排全部；持有 Controller；开看板窗口 | — |
| 看板渲染进程 | `src/renderer/` | 九个面板的 UI；**不加载目标站点** | preload 桥 + IPC |
| 被监控浏览器 | 真实 Chrome（`launch.ts` 定位） | 承载目标页面 | `--remote-debugging-pipe`（fd 3/4） |
| 存储进程 | `storage/server.mjs` | SQLite（`node:sqlite`）读写 | NDJSON over stdio |
| 代理进程 | `proxy/server.mjs` | 自签 MITM、DNS/TLS 时序、大 body 改写 | NDJSON over stdio |
| 控制服务 | `control/server.mjs` | 本地 HTTP JSON API，上游桥到主进程 | NDJSON over stdio |

外加一个非进程形态的前端：`mcp/server.mjs`（stdio MCP server，按需起、用完退），它只跟**控制服务**说话，
不直接碰主进程。

**为什么这么切**：主进程崩 = 全崩，所以它里面只留内存队列与事件分发（`技术方案.md` §5.2 的硬要求：
绝不在 CDP 事件回调里做同步 IO）。控制服务独立还多一层好处——它崩了不影响采集，agent 重连即可。

### 2.2 关键模块职责

| 模块 | 文件 | 一句话 |
| --- | --- | --- |
| Controller | `src/main/controller.ts` | 编排中枢：采集、规则、输入、控制面全部经它；对外方法即控制面能力表 |
| 采集 | `src/main/browser/collector.ts` | CDP 事件 → 内存记录 → 入队 |
| CDP 通道 | `src/main/browser/cdp.ts`、`pipe-transport.ts` | pipe 上的 CDP 客户端；多 session 管理 |
| 启动 | `src/main/browser/launch.ts` | 定位 Chrome、拼启动参数、抗节流三开关 |
| 自动化 | `src/main/browser/automation.ts` | 输入投递、导航、截图、DOM 求值 |
| 定位 | `src/main/browser/locate.ts` | selector → 元素中心点（「说选择器，不说坐标」） |
| 规则 | `src/main/rules/` | 匹配、动作、沙箱、持久化 |
| 三源关联 | `proxy/correlate.mjs` | CDP 为主键 + 时间窗 + 晚配 + drain 补报 |
| 控制桥 | `src/main/control/bridge.ts` | 主进程与控制服务子进程之间的 NDJSON RPC |
| 存储客户端 | `src/main/storage/client.ts` | 队列、批量 flush、LRU 引用 |

### 2.3 一次启动的时序（关键：先接管，再放行）

1. 主进程解析环境变量，决定数据目录、Profile、是否开代理
2. `launch.ts` 起真实 Chrome，命令行 URL 固定为 `about:blank`
3. `Target.setAutoAttach({ flatten: true })`，逐个 target attach 并 enable `Network` 域
4. **全部 attach 完**，才 `Page.navigate` 到 `MONITOR_URL`
5. 规则集下发（能由代理等价执行的那部分）、代理/存储/控制服务就绪
6. 看板窗口打开，控制服务把 `{ port, token, pid }` 写进 `<dataDir>/control.json`

第 2–4 步的顺序是本项目的命门：命令行直接传目标 URL 的话，首屏请求在 attach 之前就发完了，一条都抓不到。

## 3. 采集层设计

### 3.1 多 target 覆盖是底线

`Target.setAutoAttach({ flatten: true })` 之后，每个新 `sessionId` 都要**单独** enable 一遍 domain，
否则 OOPIF / Web Worker / Service Worker 里的流量全是黑的。现代站点相当比例的请求在 SW 里。

两条踩坑得来的纪律：

- **Service Worker 必须先放行、再 enable**。对暂停中的 SW，`Network.enable` 永不回包
  （实测挂 18s 直到管道关闭），而 `Runtime.runIfWaitingForDebugger` 就排在它后面 —— SW 卡在
  install 之前，站点半死，**CDP 侧一个错都不报**。所以 `attachedToTarget` 里遇到
  `waitingForDebugger && type === 'service_worker'`：先 `void resumeTarget(sid)`（不 await），
  再 `await enableSession()`。page / worker 保持原序。
- **同一个 target 只认一个 session**。SW 常被 root session 和 page session 各 attach 一次，
  两边都带 `waitingForDebugger`。用 `primarySession: Map<targetId, sessionId>` 保证每个 target
  只在一个 session 上开域，重复的记日志跳过，否则请求行会重复。

### 3.2 三源与各自补什么

| 源 | 给什么 | 给不了什么 |
| --- | --- | --- |
| CDP | 请求/响应头、body、时序、发起链、DOM、脚本；**主键来源** | DNS/TCP/TLS 分段；浏览器自身流量 |
| 代理 | DNS / TCP / TLS / TTFB / download 分段、上游 IP、TLS 套件、大 body 改写 | 拿不到 `resourceType` / `frameUrl` / `targetType` 这类页面侧信号 |
| 页面探针 | 「页面实际看到了什么」（响应头、注入结果、规则是否生效） | 只能覆盖注入得进去的场景 |

关联算法在 `proxy/correlate.mjs`：CDP 记录为主键，代理记录按时间窗配上去，配不上的晚配（drain 补报）。
窗口默认 1000ms（`MONITOR_PROXY_WINDOW_MS`）—— 实测 50ms 时关联率只有 21.2%，1000ms 才够。
对照真值见 `npm run verify`（受控 origin 自记 access log，逐条比对）。

### 3.3 脚本采集

JS 源码走 `Debugger` 域（`Debugger.scriptParsed` + `getScriptSource`），这是唯一能看到内联
`<script>` / `eval` / `new Function` 的路子（`Network` 只看得到网络加载的文件）。
`Debugger` 是 §3.4 点名的高风险 domain，所以**只在 Profile L 开**。

去重按内容 hash：`scripts` 存源码与元数据，`script_refs(inst, hash)` 表示「本次会话加载了哪些」。
内联脚本的 `url` 是**文档 URL**而不是空串，判内联要用 `startLine > 0`（DevTools 同款判据）。
列表查询刻意不返回源码（一页脚本可能几十 MB），要源码走 `monitor_script_source`。
## 4. 双 Profile 设计

同一套代码，两种「怎么被看见」的取舍。切换 Profile 是**收工重启**而不是热切——启动参数、
domain 白名单、采集侧的 `Debugger` 通道都钉在浏览器生命周期上，热切做不干净。

| 能力 | Profile L（默认） | Profile H |
| --- | --- | --- |
| 请求 / 响应头、body、时序 | ✅ | ✅ |
| 发起链（initiator 调用栈） | ✅ | ✅ |
| JS 源码（`Debugger`） | ✅ | ❌ 整条链失效 |
| 控制台表达式求值（`Runtime`） | ✅ | ❌ 明确拒绝，不是「静默失败」 |
| DOM 树 / 样式 / Overlay | ✅ | ✅（不依赖 `Runtime`） |
| 页面 console 回流 | ✅ | ❌ 空 |
| 探针 | 走 `Runtime` 求值 | 走注入 + 信标回传 |
| 拟人化输入 | ✅ | ✅ |

**§3.4 红线**：`Runtime` / `Debugger` 是页面最容易探到的两个 domain（隔离世界名注解、
`Error.prepareStackTrace`、DevTools 工具脚本残留）。H 面不碰它们，代价是丢掉求值与脚本源码。

**H 的判据是双向的**：探针既要不检出 CDP 痕迹，也要在 H 下走注入通道仍能拿到报告
（`npm run test:probe`，14 项，两个 Profile 各起一次容器）。

## 5. 干预引擎

### 5.1 规则模型

`RuleSet = { rules, fixtures, injections }`：

- `rules[]`：`{ id, match, action }`。匹配维度包含 URL / host / method / resourceType /
  frameUrl / status / 正则等；动作只有两类——**网络类**（block / redirect / 改请求头 / 改响应头 /
  改请求体 / 改响应体 / delay / mock）与**注入类**（注入脚本，按 `document_start` /
  `document_ready`）
- `fixtures`：给 body 模板与 mock 用的数据
- `injections[]`：注入片段

规则文件默认 `<数据目录>/rules.json`（`MONITOR_RULES` 可覆盖），面板保存与 HTTP `/rules` 写的是同一份。

### 5.2 谁来执行：CDP 侧还是代理侧

同一个动作有两个可能的执行方，**判据只有一条**：代理拿不拿得到执行所需的信息。

| 情况 | 执行方 | 原因 |
| --- | --- | --- |
| 拿得到 `content-length` 的大响应体改写 | 代理 | 大 body 走 base64 过 IPC 会把页面卡住；两侧用**同一个阈值**，正好互补 |
| 需要 `resourceType` / `frameUrl` / `targetType` 约束 | CDP | 代理拿不到这些页面侧信号，硬发会改错（日志会报条数） |
| 改响应头但拿不到 body | 放弃 | CDP 没有「只改响应头」的命令，只能重发响应，流式/大响应/304 都重发不起 |
| 其余 | CDP | 默认路径 |

**「同一条响应只应用一次」是单独验过的**（`node work/double-apply-check.mjs`，2/2，判据用**非幂等**脚本），
因为两侧都可能命中同一条规则，重复应用会把页面改坏。

### 5.3 沙箱

body 改写脚本跑在 `proxy/rule-sandbox.mjs`，**主进程与代理共用同一份实现**——两侧语义必须一致，
否则同一条规则在「大 body 走代理、小 body 走 CDP」时行为不同。自检见 `npm run test:rules`（59 项：
匹配语义 / 动作语义 / 沙箱边界）。

## 6. 控制面设计

### 6.1 一个桥，两种前端

```
agent ──HTTP──> control/server.mjs ──NDJSON──> Electron 主进程 ──> Controller
agent ──stdio──> mcp/server.mjs ─────HTTP────> control/server.mjs（同上）
```

MCP server 是**控制服务的客户端**，不是第二个实现。所以「HTTP 有的能力」与「MCP 有的能力」
天然同源：25 个 MCP 工具就是 HTTP 路由的一层薄映射。新增能力只改一处。

**为什么 MCP 不直连主进程**：MCP server 是按需起的临时进程，直连就得复制一套发现与鉴权；
挂在控制服务上，它连进程生命周期都不用管。

### 6.2 HTTP 契约

29 条路由（28 条在路由表 + `/health` 特殊处理，免鉴权）。约定：

- 真结果是响应体本身（`raw: true`），不是包一层 `{ ok, data }`
- 读路由走 `GET` + query；写路由走 `POST` + JSON body，且标 `mutating: true`
- query 有别名层：`urlPattern→url`、`domain→host`、`type→resourceType`、`q→search`、
  `initiator→initiatorType`；数值字段（status / since / until / minSize …）统一转数字
- 写路由超时更长（`/sessions/profile`、`/probe` 180s，`/navigate` 60s）

### 6.3 MCP 契约

stdio JSON-RPC，`tools/list` 恰好 25 个工具。设计约束：

- **参数用「人类/agent 的词汇」而不是坐标**：`monitor_input` 收 `selector`，
  坐标换算在 `locate.ts` 里做（页面自己算，不受缩放/滚动影响）
- **大的东西给引用不给正文**：`monitor_body` 默认给摘要 + hash，要正文才 `withData: true`；
  `monitor_script_source` 按 hash 单取；截图默认 inline 成 image 块，也可只要路径
- **失败必须显式**：H 下 `monitor_evaluate` 返回明确拒绝，绝不静默返回空值
  （agent 拿到空值会当成「页面没这个变量」）

### 6.4 鉴权与地址发现

- 绑 `127.0.0.1`，全部路由要 `Authorization: Bearer <token>`（`/health` 例外）
- token 与端口写在 `<数据目录>/control.json`，启动时写、退出时删
- 端口默认 `0`（系统分配）；`MONITOR_API_PORT` 可固定
- MCP 侧三种接法：自动 discovery → `--data-dir` 指定 → `MONITOR_CONTROL_URL` 直接给地址
- **残留 `control.json` 是经典坑**：被 kill 的应用删不掉自己那份，agent 会连上一次的死数据。
  判据是 `startedAt` 时间戳，只认本次启动之后写的

### 6.5 投递语义（动作完成 ≠ 页面已收到）

`POST /input` 返回时，事件可能还在浏览器队列里排队。实测：动作返回后页面还会继续收 ~150ms 的事件
（80 点动作后稳定在 111 点）。这条语义有两个后果：

- 调用方要「点完立刻读结果」，得留 ~200ms，或把读取并进同一次 `/evaluate`
- 验收脚本测轨迹时必须先等页面侧记录器安静（`recorderQuiet()`），否则测量窗口被污染，
  会看到「点数 149 vs 80」「单步位移 637px」这类假故障

Controller 侧对应 `settleInput()`：动作后（Profile L）用 `Runtime.evaluate` 等两帧 rAF，
`Promise.race` 兜 500ms 上限，失败静默——收尾是尽力而为，不能把已经落地的输入拖成失败。
Profile H 跳过（§3.4 红线）。

## 7. 存储设计

### 7.1 为什么是独立进程

设计文档原先写「Electron 33 没有 `node:sqlite`，用 `better-sqlite3` + `electron-rebuild`」。
**实测这条路走不通**：`better-sqlite3` v13 在 Electron 33 里 `require` 那一瞬间硬崩（exit `-36861`），
连 `new Database()` 都到不了——它虽然是 N-API prebuild，仍然不行。

改成：**系统 Node 22 起独立存储进程，用 `node:sqlite`，NDJSON RPC over stdio**。
稳定、零编译、零 ABI 风险，顺带满足「事件回调里不做同步 IO」。

### 7.2 表结构

| 表 | 存什么 | 关键索引 |
| --- | --- | --- |
| `meta` | 库版本、迁移状态 | — |
| `instances` | 每次会话（profile、起止时间） | — |
| `requests` | 一条请求一行（含 P5 的代理列） | `inst+ts`、`url`、`host`、`status`、`mime`、`resource_type`、`body_hash`、`inst+key` |
| `bodies` | body 正文 + LRU 字段 | `stored,last_ref` |
| `scripts` | 脚本源码（按 hash 全局去重） | `url` |
| `script_refs` | 「本次会话加载了哪些脚本」 | `inst,first_seen` |
| `events` | 生命周期事件流水 | `inst,ts` |

**迁移纪律**：`CREATE TABLE IF NOT EXISTS` 不会给已存在的表补列，加列必须显式迁移
（`storage/server.mjs` 里老库补 P5 代理列的代码就是这个用途）。

### 7.3 body 生命周期

采集受三个上限约束：单条（`MONITOR_BODY_MAX_KB`）、总量（`MONITOR_BODY_STORE_MB`）、
条数（`MONITOR_BODY_STORE_COUNT`）。超限只留摘要 + hash，正文按 LRU 淘汰。
库里没有时还能现捞一次（`monitor_fetch_body` / `GET /requests/:seq/body-live`），
只对**还没被浏览器驱逐**的有效。

**`/clear` 的语义是「清本次会话的采集缓冲」，不是清库**：库里的历史不动，
`/status` 的 `requestCount` / `scriptCount` 同时归零（`clear()` 里显式 `patchStatus`，
因为 `flush()` 在队列空时会提前返回，光靠它同步会读到旧计数）。
## 8. 关键设计决策（含踩坑）

每条都写「结论 / 理由 / 反悔了会怎样」，方便以后有人想推翻时知道代价。

### D1 被监控的浏览器必须是真 Chrome，不用 Electron 承载目标页面

Electron 的 `window.chrome` 不完整（缺 `loadTimes` / `csi`），是成熟的检测点。
Electron 只用来画看板——看板不加载目标站点，特征完全无害。

### D2 控制通道走 pipe 而不是端口

`--remote-debugging-pipe` 用 fd 3/4（父进程写 3、读 4），`netstat` 扫不到任何监听端口。
代价是没法用现成的 HTTP CDP 客户端，`pipe-transport.ts` 自己实现。
排查 pipe 是否可用：`node scripts/probe-pipe.mjs`。

### D3 被监控浏览器必须带抗节流三开关

`--disable-backgrounding-occluded-windows`、`--disable-renderer-backgrounding`、
`--disable-features=CalculateNativeWinOcclusion`。

**踩坑过程**：症状是「导航后 `POST /input` 变慢/超时」。误判过几次（`Page.bringToFront` 无效、
focus emulation 看着有效其实是运气）。真因是**窗口被别的窗口盖住**时 Chromium 按「不可见」节流渲染，
`Input.dispatchMouseEvent` 的回执被压到**恰好 ~5005ms**（一个超时常量），一次 8 点轨迹要 40s，
调用方 12s 就超时了。决定性证据是直接查正在跑的应用：页面自报 `outerWidth:159, outerHeight:27`
（窗口被挤成一条）。`netstat`、主进程健康检查全都正常，**只有窗口几何能看出真相**。

**反悔的代价**：去掉这三个开关，慢页面上的鼠标/键盘投递会退化成 5s/次。

### D4 三源关联窗口默认 1000ms

实测 50ms 时关联率只有 21.2%。代理与 CDP 看到的是同一条请求的两个视角，时间戳来源不同，
窗口太窄就配不上，太宽会出歧义（`ambiguous` 计数就是给它准备的）。

### D5 代理用 SPKI pin，不碰系统信任库

自签 CA 的私钥落在 `<数据目录>/proxy-ca.key`（`MONITOR_PROXY_KEY` 可覆盖），
**复用同一把**——这样重启后 SPKI 不变，被监控浏览器那边钉一次就够。
代价是开代理后出站 TLS 指纹是 Node 的（不是 Chrome 的 JA3/JA4），所以默认关着。

### D6 大 body 改写的分界是 `content-length`

CDP 与代理两侧用同一个阈值（`MONITOR_PROXY_REWRITE_MB`）。判据只有一条：
拿得到 `content-length` 就下沉到代理，拿不到（chunked / 流式 / SSE）两侧都不改，如实记原因。
二进制与 CDP 那条路一样跳过（utf8 往返会把字节改坏）。

### D7 `/clear` 清缓冲不清库

库是持久记录，缓冲是本次会话的观察窗口。两者语义不同，混起来会让「清一下重新看」
毁掉历史。计数归零必须显式推状态（见 §7.3）。

### D8 控制窗口用自绘标题栏（`frame: false`）

控制窗口是产品门面，系统标题栏（浅色、方块按钮、Alt 菜单栏）和这套深色 UI 是两种东西，
所以 `frame: false` 一个像素都不留，标题栏自己画（`src/renderer/src/components/TitleBar.tsx`）。
顺带把「刷新 / 清空 / 数据目录」三个**全局**动作从工具栏和页脚收到顶栏右侧 —— 它们不属于
任何一个面板，散在下面既难找又占地方。

三个必须记住的点：

1. **拖动区里的按钮要显式 `no-drag`**。CSS 里统一给了 `.titlebar button`，
   漏一个的表现是「点刷新变成拖窗口」，而且不报错，很难查。
2. **双击最大化交给系统，渲染层不要再挂 `onDoubleClick`**。`-webkit-app-region: drag`
   的区域在 Windows 上就是标题栏（`HTCAPTION`），系统自己处理双击最大化与拖边吸附。
   实测（`SendInput` 级真实鼠标）：带不带渲染层处理器，`monitor:window-maximized`
   的事件序列都是 `[true]` —— caption 区的 dblclick 不会派发给渲染进程，
   那个处理器是纯多余的，留着只会在别的平台或 Electron 版本上多一次「和系统对切」的机会。
3. **最小化 / 最大化 / 关闭走 `BrowserWindow.fromWebContents(event.sender)`**，
   不要用模块级的 `controlWindow`。多会话设计（§10）将来要开多个控制窗口，
   用 sender 反查才能各管各的；「关闭」用 `win.close()` 而不是 `app.exit()`，
   这样 `window-all-closed` 里停控制服务、排空采集队列的收工逻辑不会被绕过。

窗口状态（最大化 / 还原）由主进程的 `maximize` / `unmaximize` 事件推给渲染层，
而不是只靠点击回调 —— 拖边、`Win+↑`、系统吸附都会改状态，只看点击回调会显示错图标。

## 9. 测试与验收策略

### 9.1 三条纪律

1. **判据必须外部可观测**。不采信引擎自述：完整性对照受控 origin 的 access log（`npm run verify`）；
   输入轨迹对照**页面侧**记录的真实 DOM 事件；规则生效对照页面回报（`/api/rules-report`）
2. **纯逻辑与真浏览器分开**。规则引擎、关联算法、存储都能在不起浏览器的情况下自检
   （`test:rules` 59 / `test:correlate` 30 / `test:storage` 54），跑得快、定位准
3. **性能判据不能自欺**。`test:page-perf` 三臂对照（无监控 / L / H），取页面稳态负载而不是「我觉得快了」

### 9.2 分层与分工

| 层 | 用例 | 特征 |
| --- | --- | --- |
| 纯逻辑 | `test:rules`、`test:correlate`、`test:storage` | 秒级，不碰浏览器 |
| 面板 | `test:dom`、`test:sessions`、`test:detail`、`test:ui-perf` | 真开 Electron，走 `window.monitor`（preload + IPC + Controller 的真实链路） |
| 采集 | `verify`、`test:scripts`、`test:proxy`、`test:proxy-e2e` | 真开 Chrome + 受控 origin |
| 干预 | `test:rules:e2e`、`test:input`、`test:probe` | 判据在页面侧 |
| 控制面 | `test:control`、`test:drill`、`test:smoke` | HTTP / MCP 真调用 |

`test:smoke` 是「一条都不落」的那张网：29 条 HTTP 路由 + 25 个 MCP 工具逐个真调用。
`test:drill` 是唯一**纯 MCP** 的端到端演练（agent 视角走完整条链路，到「规则真的生效」为止）。

### 9.3 跑全量时的工程纪律

- 每个 suite 前后 `taskkill /F /IM electron.exe /T` **和** `/F /IM chrome.exe /T`
  ——被监控的是真 Chrome，不是 Electron 的子进程
- **端口分区**避免撞车：detail `9487` · drill `9488`/`9495` · smoke `9507`/`9498` · 调试 `9511–9532`
- 每个 suite 用独立数据目录（残留 profile 会被 Service Worker 带脏）
- 验收脚本跑的是 `out/main/index.js`，**改完必须 `npm run build`**

放齐之后的总入口就是 `work/regress2.ps1` 那种串行脚本（18 个 suite，约 5 分钟）。

## 10. 扩展点

**加一个 MCP 工具**：`mcp/server.mjs` 里加一条 `tools` 定义 + 一个 `case`（映射到已有 HTTP 路由）。
新能力落在 Controller 上，HTTP 与控制服务各加一条路由，MCP 只是薄映射。

**加一个面板**：`src/renderer/src/components/` 加组件，`App.tsx` 挂 tab，
`src/shared/types.ts` 加数据形状，`src/main/index.ts` 加 IPC handler，preload 暴露方法。
如果数据要落库，先在 `storage/server.mjs` 加表 + 查询。

**加一条规则动作**：`src/main/rules/` 里加匹配/动作定义，判断它归 CDP 侧还是代理侧执行（§5.2），
两侧都要能跑就抽到 `proxy/rule-sandbox.mjs` 共用的实现里。

**加一个采集源**：新源要提供「CDP 记录之外的证据」。挂到 `correlate.mjs` 的关联里，
并在 `verify` 里加真值对照——不然它是不是真的在工作无法证伪。

详见 `docs/P4-P7-待办与阻塞.md`。

**固有盲区（设计声明，不是待办）**、**使用侧注意事项**：完整列表见 `README.md` 的「已知限制」一节，
其中对使用者影响最大的三条：

- Worker / Service Worker 会话不发 `Network.*ExtraInfo` → 这部分请求没有请求/响应头
- `/input` 返回 ≠ 页面已收到（见 §6.5）
- 抗节流三开关的代价：页面被遮挡时仍按「可见」跑，靠后台节流做手脚的页面能看出差异
