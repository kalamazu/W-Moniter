# 多会话监视器 · 设计与用法

> 目标：把它从「一次运行 = 一个看板绑一个 Chrome」改成
> **一个常驻监视器，由它按需开 0..N 个受监控 Chrome**，并且能打包成可执行文件。
> 本文是这个改动的用法模型 + 架构 + 分期与验收判据。

## 1. 用法模型（改成什么样）

**现在**：`npx electron .` → 一个看板 + 一个受监控 Chrome，一一绑定，想换站点就重开。

**改成**：

```
[监视器窗口]                          ← 一个，常驻
  ├─ 会话条： [会话 1] [会话 2] [+]    ← 点 + 新建
  └─ 面板区（9 个 tab）                ← 永远显示「当前选中会话」的数据

[受监控 Chrome A]  ← 会话 1           ← 各自独立进程、独立 profile
[受监控 Chrome B]  ← 会话 2
```

三个动作就是全部用法：

| 动作 | 做什么 | 结果 |
| --- | --- | --- |
| **新建会话** | 起一个新 Controller + 一个受监控 Chrome | 会话条多一个标签，新 Chrome 窗口出现 |
| **切换会话** | 换「当前会话」 | 9 个面板整体切到那个会话的数据 |
| **关闭会话** | 体面收工：收采集队列 → 关 Chrome → 关代理 | 该会话从条上消失，库里历史保留 |

**为什么要多会话**：对比实验（同站点不同 Profile / 不同规则集）、并行观测多个站点、
一个会话被页面搞挂了不影响另一个。这也是「监视器」这个词的本意 —— 它是容器，不是单个抓包会话。

### 1.1 明确不做的

- **不做跨会话聚合视图**。统计 / 瀑布图都是「当前会话」的。库里能按 inst 查是另一回事
- **不做会话模板/批量启动**（一次开 10 个）—— v1 手动开，够用再说
- **不做会话持久化恢复**（重启监视器不自动恢复上次的会话）—— 历史在库里，重开就行

## 2. 会话是什么（数据模型）

一个**会话** = 一个 `Controller` 实例 = 一行 `instances` 记录。它自己拥有：

| 归属 | 说明 |
| --- | --- |
| 一个受监控 Chrome 进程 | 独立 profile 目录（`<dataDir>/sessions/<sid>/browser-profile`） |
| 一个 `inst` id | 库里所有表都带 `inst` 列，天然分区 |
| 一组启动参数 | URL / Profile L\|H / headless / 抗节流三开关 |
| 一个代理进程（可选） | 默认关；开了才有 DNS/TLS 时序 |
| 自己的规则集？ | **不是** —— 见下 |

**规则集是监视器级（全局）的**，不是会话级。理由：规则表达的是「我想怎么干预这类流量」，
跨会话共享才符合直觉；而且 `rules.json` 落在数据目录，本来就是全局文件。
代价是没法 A/B 两套规则——这属于「以后再说」，不放进 v1。

**存储是监视器级共享的**：一个存储进程 + 一个 `monitor.db`。
可行性来自现有协议：`storage/server.mjs` 的每个方法都逐次带 `inst` 参数
（`beginInstance` 只负责分配 id），本来就是无状态的，多个 Controller 共用一个客户端没有冲突。
这也是 v1 唯一一处必须动的既有代码 —— 现在是「每个 Controller 起一个存储进程」，
两个会话就是两个进程写同一个库，没必要且有争用风险。

## 3. 架构改动

### 3.1 主进程：单例 Controller → SessionManager

```
SessionManager
  ├─ sessions: Map<sid, Session>      Session = { sid, controller, url, profile, createdAt, ... }
  ├─ activeSid: string
  ├─ open(options) → sid              新建（起 Controller + 等连接）
  ├─ close(sid)                       体面收工
  ├─ get(sid?)                        取会话；不传 = active
  └─ list()                           会话条的数据源
```

**改动面**：`src/main/index.ts` 那 30 多个 IPC handler 目前都闭包在单例 `controller` 上，
统一改成 `manager.get(sessionId?)`。这是纯机械改动，但量大 —— 每个 handler 多一个
可选的首参 `sessionId`。

### 3.2 存储：一个进程，多会话共用

`storage/client.ts` 加一层按 `dbPath` 缓存的共享注册表：

- `ensureProcess(config)` —— 起进程、握手（幂等，多个会话只起一次）
- `beginInstance(instance)` —— 每个会话分配自己的 `inst`
- 其余方法照旧带 `inst`

这样 `Controller` 拿到的还是「一个 StorageClient」，但底层共用同一个子进程。
好处：进程数从 `1 + N` 降到 `1 + 1`，且不会被两个进程同时写同一个库。

### 3.3 控制面：一个端口，会话用参数选

**不新增端口**——端口数等于会话数会让 agent 侧配置爆炸。改成：

| 变化 | 说明 |
| --- | --- |
| 每条既有路由接受 `?session=<sid>` | 省略 = 当前 active 会话（保持向后兼容，现有 29 条路由的调用方不用改） |
| 新增 `POST /sessions/open` | body 同启动参数（`url` / `profile` / `headless`），返回 `{ sid }` |
| 新增 `POST /sessions/close` | body `{ sid }` |
| 新增 `POST /sessions/activate` | body `{ sid }`，切 active |
| `/status` 增加 `sessions[]` | 会话条 + `activeSid`；`/status` 自身的字段仍是「当前会话」的 |

### 3.4 MCP：加一个会话维度

- 25 个既有工具加**可选** `session` 参数（省略 = active），所以现有 agent 调用零破坏
- 新增 `monitor_open_session` / `monitor_close_session` / `monitor_activate_session`
- 既有 `monitor_sessions` 升级为「会话 + 实例」双视图

对 agent 的价值：它能真正「开一个新的干净浏览器做对比实验」，而不是只能操作唯一那个。

### 3.5 渲染层

- 顶部加**会话条**：每个会话一个标签（URL 主机 + Profile 徽标 + 请求计数 + 状态点），末尾 `+`
- `useRequests` 等 hook 的请求带上 `activeSid`；切会话 = 换 `sessionId` 重新拉
- 「会话」tab 从「历史实例列表」改成「**活跃会话管理**」：新建 / 关闭 / 切 Profile / 打开 devtools 入口

## 4. 打包成可执行文件

### 4.1 一个绕不开的外部依赖

**存储 / 代理 / 控制服务都是 Node 子进程**（`node:sqlite` 是选它们的理由，见设计文档 §7.1）。
Electron 自带的 Node 跑不了这些 `.mjs`（`node:sqlite` 在 Electron 里不可用，而且它们是独立进程）。
所以「双击就能用」的前提是**包里自带一份 Node 运行时** —— 不能指望用户机器上装了 Node 22。

方案：把官方 Node 22 的 `node.exe` 作为 `extraResources` 打进包，打包模式下
`locate-node` 优先用它；开发模式下仍用系统 Node。

### 4.2 三个必须处理的打包坑

| 坑 | 处理 |
| --- | --- |
| `control/` `mcp/` `storage/` `proxy/` 是**独立 .mjs 进程**，打不进 asar | `asarUnpack` 这几个目录（或直接按 `extraResources` 摊在 resources 下） |
| 代码里用 `join(root, 'storage/server.mjs')` 定位它们 | 打包后 `root` 必须指向解包后的真实路径，不能用 `app.getAppPath()`（asar 内的路径 spawn 不了） |
| 用户机器上的 Chrome 路径 | 保持「自动查找 + `CHROME_PATH` 覆盖」，**不内置浏览器**（内置就不是真 Chrome 了，正是要避免的） |

### 4.3 产物形态

| 形态 | 用途 |
| --- | --- |
| **portable（免安装单目录）** | 主交付：解压即用，适合本机与拷贝走 |
| NSIS 安装包 | 次要：给需要开始菜单/卸载项的场合 |

## 5. 分期与验收判据

每一期独立可验收，做完一期就能用。

### P1 存储共享 + SessionManager（内核）
- 判据：一次运行内开 2 个会话，两个都有独立 `inst`、独立 profile、都能采到流量；
  `netstat` 里**只有一个**存储子进程；两个会话的请求在库里按 `inst` 分得开
- 回归：现有 18 个 suite 必须仍然全绿（尤其 `test:sessions` 与 `test:storage`）

### P2 会话条 UI
- 判据：新建 → 切 → 关 三个动作在界面上走通；切会话时 9 个面板都换数据源，不串台；
  关闭会话后该 Chrome 窗口真的消失、库里 `instances.ended_at` 有值

### P3 控制面 + MCP
- 判据：`POST /sessions/open` 起会话 → 用 `?session=` 对它查请求 → 关掉；
  省略 `session` 时行为和现在完全一致（老调用方零改动）
- 回归：`npm run test:smoke` 必须仍 59/59（证明向后兼容），再补多会话用例

### P4 打包
- 判据：产出的 portable 包在**没装 Node 的路径假设下**能跑（用自带 node.exe）；
  能新建会话并采到流量；`npm run test:drill` 的 MCP 接法在打包产物上仍然可用
- 注意：打包产物验收至少要留一个「真开 Chrome 抓到真流量」的证据，不能只看进程起没起来

## 6. 风险

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 存储共享引入跨会话串台 | 数据错乱（最难查的一类） | 「同一份 mergeCache 键含会话」这类既有约束要保持；验收必须**两个会话同时打同类请求**看会不会串 |
| 多会话 = 多 Chrome，内存/CPU 线性涨 | 开 5 个会话机器吃力 | 会话条显示每会话请求数；文档写明建议上限；不做自动限制 |
| asar / 路径在打包后才暴露问题 | 「开发能跑，打包不能」 | P4 的判据里明确要求**在打包产物上**跑一次真采集 |
| 抗节流三开关在多个窗口间互相遮挡 | 又是那个 5s/次的老问题（见设计文档 D3） | 多开窗口时窗口会互相盖住 → 必须保持三开关开着；这条要写进使用手册 |
