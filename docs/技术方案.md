# 监控容器 · 技术方案

> 目标：在高隐蔽性前提下，对 Chromium 实例做到**完全的信息采集**与**强力的运行时干预**。
> 文档状态：v1 草案，待评审。术语中「采集」指观测，「干预」指改写/注入/执行控制。

---

## 1. 目标与非目标

### 1.1 三个硬目标

| 目标 | 具体含义 | 主要矛盾 |
| --- | --- | --- |
| 高隐蔽性 | 目标站点无法通过常规手段识别出自动化/调试环境 | 与控制力直接冲突 |
| 完全信息控制 | 语义层 + 字节层信息齐备，可与采集源交叉验证 | 单源必有盲区 |
| 强执行控制 | 改写请求响应、注入、输入、断点、读改变量 | CDP 控制力最强但可检测 |

### 1.2 非目标

- 不做通用代理抓包工具（Fiddler/Charles 的替代）
- 不做分布式采集集群，单机多实例即可
- 不做爬虫调度系统，本方案只负责「单实例的观测与干预」

## 2. 总体架构

核心设计原则：**被监控的浏览器保持绝对干净，所有包装都在进程外。**
包装得越深，特征越多；最高隐蔽性的形态是「不套壳」。

```
┌──────────────────────────────────────────────────────────────────┐
│  Controller  (Electron + TypeScript)                             │
│                                                                  │
│  ┌────────────┐ ┌────────────┐ ┌──────────┐ ┌────────────────┐   │
│  │ 监控看板    │ │ 规则引擎    │ │ 事件存储  │ │ ChannelManager │   │
│  │ (React)    │ │ (匹配/执行) │ │ (SQLite) │ │  通道抽象+切换  │   │
│  └─────┬──────┘ └─────┬──────┘ └────┬─────┘ └───────┬────────┘   │
│        └──────────────┴─────────────┴───────────────┘            │
└───────────┬──────────────────────┬──────────────────┬────────────┘
            │ CDP over pipe        │ 代理控制通道       │ 探针回传
            │ (fd3/fd4, 无端口)     │ (UDS/TCP local)   │ (binding)
            ▼                      ▼                   ▼
   ┌─────────────────┐   ┌──────────────────┐  ┌──────────────┐
   │ Chromium 实例    │   │ 本地代理          │  │ 页面内探针    │
   │ · 有头 / 真实GPU │──►│ · 字节层采集      │  │ · hook fetch │
   │ · 独立进程       │   │ · TLS 解密        │  │ · hook XHR   │
   │ · 零污染         │   │ · 大文件改写      │  │ · hook WS    │
   └─────────────────┘   └──────────────────┘  └──────────────┘
```

### 2.1 为什么是这个拓扑

| 决策 | 理由 |
| --- | --- |
| 浏览器独立进程，不用 Electron 承载 | Electron 的 `window.chrome` 不完整（缺 `loadTimes`/`csi`），是成熟的检测点 |
| 用 `--remote-debugging-pipe` 而非 `--remote-debugging-port` | pipe 走 stdin/stdout，不开网络端口，`netstat` 扫不到 |
| UI 用 Electron | UI 不加载目标站点，Electron 特征完全无害，开发效率高一个数量级 |
| 字节层用代理而非改 `net/` | 拿到同样的 DNS/TLS/帧信息，但完全不用编译，成本差两个数量级 |
| 不做 Tauri/Wails | 它们用系统 WebView，不是 Chromium，没有 CDP，方向性错误 |

## 3. 双通道设计（Profile L / Profile H）

这是本方案的核心。**同一套上层 API，两套底层实现，按目标站点的检测强度切换。**

### 3.1 通道抽象

上层（看板、规则引擎）只依赖接口，不关心底层是 CDP 还是私有通道：

```ts
interface ControlChannel {
  // ---- 观测 ----
  onRequest(cb: (e: RequestEvent) => void): Disposable
  onResponse(cb: (e: ResponseEvent) => void): Disposable
  onFrame(cb: (e: FrameEvent) => void): Disposable

  // ---- 干预 ----
  block(match: Match): Disposable
  rewriteRequest(match: Match, fn: RequestTransformer): Disposable
  rewriteResponse(match: Match, fn: ResponseTransformer): Disposable
  inject(script: string, opts: InjectOptions): Disposable
  input(evt: InputEvent): Promise<void>

  // ---- 执行控制 ----
  evaluate(expr: string, frameId?: string): Promise<unknown>
  capabilities(): CapabilitySet      // 声明本通道支持哪些能力
}
```

`capabilities()` 是关键：Profile H 下 `breakpoint` 等能力返回 `false`，UI 据此禁用对应按钮，而不是运行时报错。

### 3.2 能力矩阵

| 能力 | Profile L | Profile H | 说明 |
| --- | --- | --- | --- |
| 网络全量观测 | ✅ CDP `Network` | ✅ CDP `Network` | 低风险 domain，H 下保留 |
| 请求/响应体获取 | ✅ `Network.getResponseBody` | ✅ `Fetch` 阶段拦截 | H 下用 Fetch 更可靠 |
| 请求改写 | ✅ `Fetch.continueRequest` | ✅ 同 | |
| 响应改写/伪造 | ✅ `Fetch.fulfillRequest` | ✅ 同 | |
| 脚本注入 | ✅ 多手段 | ⚠️ 仅 `addScriptToEvaluateOnNewDocument` | 不用 `Runtime.evaluate` |
| 断点/单步 | ✅ `Debugger` | ❌ | H 下必须放弃 |
| 读改变量 | ✅ `Runtime.evaluate` | ⚠️ 靠注入 hook 回传 | 能力降级 |
| 输入自动化 | ✅ `Input.dispatch*` | ✅ 同 | dispatch 本身无痕 |
| 指纹伪装 | ✅ `Emulation.*` | ❌ 改用启动参数 + 二进制 patch | Emulation 有特征 |
| DOM/CSS 检查 | ✅ | ⚠️ 按需临时开 | |
| 性能分析 | ✅ | ❌ | |
| CDP 痕迹 | 有 | 最小 | 见 §3.4 |

### 3.3 Profile L — 直连模式

适用于：内部系统、自有站点、无风控目标、开发调试期。

- 基座：官方 Chromium，headful
- 连接：CDP over pipe
- Domain：全开
- 注入：`addScriptToEvaluateOnNewDocument` / `Runtime.evaluate` / `Page.createIsolatedWorld`
- 指纹：`Emulation.*`
- 特点：**功能 100%**，开发迭代最快，接受 CDP 可检测

### 3.4 Profile H — 隐蔽模式

适用于：有反自动化、反爬、CDP 检测的目标站点。

- 基座：**自编译 Chromium** + 反检测补丁（参考 `rebrowser-patches` 类做法）+ 指纹补丁
- 连接：CDP over pipe，**只开白名单 domain**
- Domain 白名单：`Page`、`Network`、`Fetch`、`Target`
- **禁用**：`Runtime`（最经典检测点）、`Debugger`、`Profiler`、`HeapProfiler`、`Console`、`Log`、`Emulation`
- 注入：只用 `Page.addScriptToEvaluateOnNewDocument`
- 执行控制：从「断点」降级为「**Hook + 回传**」
- 指纹：启动参数 + 二进制 patch（不用 Emulation）

**Domain 风险分级表**（选择白名单的依据）：

| Domain | 页面可检测性 | L | H |
| --- | --- | --- | --- |
| `Target` | 无（浏览器层） | ✅ | ✅ |
| `Page` | 低 | ✅ | ✅ |
| `Network` | 低 | ✅ | ✅ |
| `Fetch` | 低（注意时序扰动） | ✅ | ✅ |
| `DOM` / `CSS` | 低 | ✅ | ⚠️ 按需 |
| `Console` / `Log` | 低 | ✅ | ❌ |
| `Emulation` | 中（会与真实环境不一致） | ✅ | ❌ |
| `Profiler` / `HeapProfiler` | 中 | ✅ | ❌ |
| `Runtime` | **高** | ✅ | ❌ |
| `Debugger` | **高** | ✅ | ❌ |

**为什么 `Runtime.enable` 是红线**：启用后 V8 的 console 调用会走不同的代码路径，实测耗时明显变化。页面只要测一下 `console.debug()` 前后的时间差就能判定「有调试器连着」。此外 `Function.prototype.toString` 与执行时序也会出现异常。这是目前最广为人知的 CDP 检测手段。

本机标定（Chrome 153 / Windows 11，各 400 次 `console.debug` 取三轮最小值）：**无 Runtime 4.25~5µs/次；有 Runtime 24.75 / 33 / 36.5 / 39.25 / 53.75µs/次**。两簇之间是 5 → 25 的空档，探针判据落在空档中间取 **15µs**（≥15 判失败，8~15 判「偏高，建议复测」）。标定过程与三条实测发现见 §8.4。

### 3.5 Profile H 下的「Hook + 回传」设计

放弃断点后，用注入的 hook 替代：

```
注入脚本 (document_start)
  ├─ 包裹 fetch / XHR / WebSocket / sendBeacon
  ├─ 包裹 crypto.subtle.* / JSON.parse / atob
  └─ 命中关注点时：
       ① 直接改行为（就地拦截/改写返回值）
       ② 通过 Runtime.addBinding 注册的 native 函数回传事件
```

`Runtime.addBinding` 的价值：它创建的是**真正的 native function**，`toString()` 返回 `[native code]`，比纯 JS 注入干净得多。但它仍会出现在 `Object.getOwnPropertyNames(window)` 里，命名要有策略（混入看起来合理的名字）。

### 3.6 Profile 选择机制

不要靠人猜。做一个**检测探针**，在目标站点上跑一组自检，输出报告：

| 检测项 | 方法 |
| --- | --- |
| CDP 痕迹 | 复现 console 时序检测、`navigator.webdriver`、错误栈特征 |
| 指纹一致性 | WebGL vendor/renderer、Canvas hash、Audio hash、字体列表 |
| 行为检测 | 是否有鼠标轨迹校验、请求节奏校验 |
| TLS 指纹 | 与真实浏览器 JA3/JA4 对比 |

探针报告 → 推荐 profile → 人工确认。**让 Profile 切换有数据支撑，不是拍脑袋。**

## 4. 采集层（三源）

单源必有盲区，三源交叉验证才叫「完全的信息控制」。

| 源 | 覆盖 | 独有信息 | 盲区 |
| --- | --- | --- | --- |
| **CDP** | 语义层 | 响应体、JS 源码、DOM、调用栈、initiator | DNS、TLS、字节、浏览器自身流量 |
| **代理** | 字节层 | **DNS 查询、TLS 握手、JA3、HTTP/2 帧、真时序** | 不懂 Web 语义 |
| **页面探针** | 页面视角 | hook 到的调用参数、页面内部状态 | 只能看到注入点之后 |

### 4.1 CDP 采集：必须处理多 target

**这是最容易做错的地方。** 默认只 attach 到主 frame，Worker 和 Service Worker 的流量全部漏掉 —— 而现代站点一半的请求在 SW 里。

```
webContents.debugger / pipe session
  │
  ├─ Target.setAutoAttach({ autoAttach: true, waitForDebuggerOnStart: true, flatten: true })
  │
  └─ 收到 Target.attachedToTarget 事件
       └─ 拿到 sessionId + targetInfo.type
            ├─ page        → Network.enable / Fetch.enable / Page.enable
            ├─ iframe      → 同上（OOPIF 是独立 target）
            ├─ worker      → 同上
            ├─ shared_worker → 同上
            └─ service_worker → 同上
```

**每个新 sessionId 都必须重新 enable 一遍**，否则那个 target 是黑的。

**但 Service Worker 要反着来：先放行，再 enable。** 对暂停中的 SW，`Network.enable`
**永不回包** —— 实测挂 18275ms 直到管道关闭，而 `Runtime.runIfWaitingForDebugger`
就排在它后面（其余命令 2ms 就返回，只有它卡住）。后果是 SW 停在 install 之前，
`navigator.serviceWorker.register()` 的 Promise 永不 resolve，站点半死，
而 **CDP 侧一个错都不报**。所以 `attachedToTarget` 里遇到
`waitingForDebugger && type === 'service_worker'` 要先 `void resumeTarget(sid)`
（不 await）、再 `await enableSession()`；page / worker 保持原序。

**同一个 target 只认一个 session。** SW 常被 root session 和 page session 各 attach 一次，
两个 sessionId 都带 `waitingForDebugger`，各开一遍域就会导致请求行重复。
用 `primarySession: Map<targetId, sessionId>` 保证每个 target 只在一个 session 上开域，
重复的记日志跳过。

### 4.2 响应体的可靠性

`Network.getResponseBody` 依赖资源仍在 buffer，大响应/流式/被驱逐的都拿不到。两个措施：

1. `Network.enable` 时调大缓冲：`maxTotalBufferSize` / `maxResourceBufferSize` / `maxPostDataSize`（默认值很小，不改必踩坑）
2. **要稳定拿 body 就改用 `Fetch` 在 Response 阶段拦**：`Fetch.requestPaused` → `Fetch.getResponseBody` → 记录 → `Fetch.continueResponse`

Profile H 下同样用 `Fetch`，因为它在白名单里。

**「页面不读 body」是另一条坑**：`fetch(u).then(r => r.status)` 这种不消费响应体的调用，
Chrome 不发 `Network.loadingFinished` —— 请求要等到会话收尾 `flushInflight` 才落库，
其间整段不可见（`status IS NULL` 的筛选永远是空的）。对策是**先落一行 pending、
终态到了再 upsert**：一条请求最多写两次，但任何时刻列表里都能看见它。

### 4.3 三源关联

- CDP：`requestId` + `timestamp`(monotonic) + `wallTime`
- 代理：`flowId` + 本地时间戳
- 关联键：`method + url + 时间窗口`；**以 CDP 为主键**，代理记录作为补充字段 merge 进去（DNS/TLS 时序）
- 并发同 URL 会歧义 → 标 `merge_ambiguous`，**不静默配错**；关联失败保留两条（`cdp-only` / `proxy-only`），**不要丢弃**
- 键里必须带 URL（`mergeCacheKey = key + '\u0000' + url`，见 `proxy/correlate.mjs`）：
  重定向会**复用同一个 `requestId`**，只按 key 关联时第二条记录会抄走第一条的结果，
  它自己的代理 flow 反而永远没人认领（实测踩过：189 条里 7 条被串台）

**窗口是实测定的，不是拍的（§12 那条 ≥95% 全靠它）：**

| 窗口 | 受控关联率 | 说明 |
| --- | --- | --- |
| 50ms | 21.2% | 先验值。代理侧突发排队 50~57ms，全落在窗口外 |
| 200ms | 100% | 但另一轮负载下排队到过 171ms，余量只剩 1.2× |
| **1000ms** | 100% | **定案值**（`proxy/correlate.mjs` 的 `DEFAULT_WINDOW_MS`，`MONITOR_PROXY_WINDOW_MS` 可覆盖） |

窗口放大换来的是「宁可晚配也不配错」：1000ms 下 `ambiguous` 实测为 0 —— 同一 key 同一 URL
出现第二条时两侧都不认领，如实记成歧义，而不是随便配一个。

**长连接（SSE / 流式）走「先补报 + 晚配」**：这类响应在代理侧永远等不到 `end`，
`finish(flow)` 从来不会被调用，不补报就等于整条不可见。两条补救：

1. 收工前 `ProxyClient.drain()` 让代理把还在飞的 flow 以 `open: true` 补报出来（`download`
   这类字段本来就不存在，不假装完整）。顺序不能换：**先 drain 再 stop**，否则不是没有 flow，
   而是根本没有代理进程可问；
2. 代理 flow 可能比 CDP 记录**晚到**。`correlate.mjs` 给每个没配上的 CDP 记录留一个
   `cdpWaiters`，晚到的 flow 反向认领（`tryLateMatch`），命中时把计数从 `cdpOnly` 挪到 `merged`、
   并让 `flush()` 跳过已被认领的 flow —— 否则每次收工都会凭空多出一批「采集盲区」。

## 5. 数据模型与管道

### 5.1 统一事件模型

```ts
interface RequestRecord {
  id: string
  cdpRequestId?: string
  proxyFlowId?: string

  url: string
  method: string
  status?: number
  resourceType: string
  mimeType?: string

  requestHeaders: Record<string, string>
  responseHeaders: Record<string, string>
  requestBody?: BodyRef      // 二进制安全，默认只存前 256KB
  responseBody?: BodyRef

  timings: {                 // 代理给真时序，CDP 给不了 DNS/TLS
    dns?: number; connect?: number; tls?: number
    ttfb?: number; download?: number
  }

  initiator?: { type: string; stack?: CallFrame[] }
  targetId: string           // 归属哪个 frame/worker/SW
  sessionId: string
  frameUrl?: string

  fromCache: boolean
  fromServiceWorker: boolean
  size: number
  mergeState: 'merged' | 'cdp-only' | 'proxy-only'
}
```

P5 落地后新增的列（`storage/server.mjs` 的 `PROXY_COLUMNS`，schema v4 → v5，老库启动时自动 `ALTER TABLE` 补列）：

- 关联：`merge_state`、`merge_ambiguous`、`proxy_flow_id`、`proxy_open`
- 代理侧网络时序：`net_dns_ms` / `net_connect_ms` / `net_tls_ms` / `net_download_ms` / `ttfb_ms`
- 连接事实：`upstream_ip` / `tls_version` / `tls_cipher` / `upstream_alpn`
- 排队：`proxy_delta_ms`（同一条请求在 CDP 与代理两侧的时间戳差，看板上就是那段灰色排队条）

`ttfb_ms` **只能**来自代理：CDP 给不了首字节时刻（`Network.responseReceived` 是响应头到齐、
`loadingFinished` 是全部到齐），拿它们顶替会系统性偏大。看板上的五段网络条
（DNS/TCP/TLS/TTFB/download）画的就是这几列。

### 5.2 管道与背压

```
采集源 ──► 归一化 ──► 关联 ──► 过滤/采样 ──► 环形缓冲 ──┬─► SQLite 落盘
                                                     └─► 批量推送 UI
```

硬性要求：

- **绝不在事件回调里同步写盘**。重度页面每秒可产生数万条 CDP 事件，同步 IO 必卡死。
- `Network.dataReceived` 这类高频事件按 100ms 窗口聚合后再 flush。
- 背压策略：**丢采样，不丢全量元数据**。元数据永远完整，body 可采样。
- 推 UI 用 `MessageChannelMain` 传端口，**不要逐条 `ipcRenderer.send`**。

P5 的代理是**独立 node 进程**（`proxy/server.mjs`，NDJSON over stdin/stdout），理由和存储进程一样：
socket 读写与 body 改写不能和 UI 抢事件循环。两条踩出来的纪律：

- **`execFileSync` 这类同步调用会阻塞事件循环**：同一个进程里刚 `listen` 的端口，Chrome 死活连不上
  （踩过）。代理、存储都必须 `spawn` 子进程，不能图省事 `require` 进来；
- 收工顺序有硬约束：`await proxy.drain()` → `await this.stop()`。drain 必须在 stop 之前 ——
  长连接（SSE）在代理侧的 flow 只有 drain 才报得出来。

### 5.3 存储

| 数据 | 存法 |
| --- | --- |
| 请求元数据 | SQLite，索引 `url` / `host` / `status` / `mime` / `ts` |
| 请求响应体 | 单独表存 blob，LRU 淘汰，超阈值只留摘要 + hash |
| JS 源码 | **按内容 hash 去重**存（`scriptId` 每个会话都不一样，用它去重等于没去重） |
| 时序明细 | 按会话分表，支持整段导出 |

> **实测结论（已落地）**：Electron 33 内置 Node 20.18 没有 `node:sqlite`；
> 而 `better-sqlite3` v13 在 Electron 33 里 `require` 那一瞬间就**硬崩**（exit `-36861`），
> 连 `new Database()` 都到不了 —— 它虽然是 N-API prebuild，仍然不行。
> 所以存储做成**独立进程**：系统 Node 22 + `node:sqlite`，NDJSON RPC over stdio。
> 零编译、零 ABI 风险，并顺带满足 §5.2「绝不在 CDP 事件回调里同步写 IO」。
> 实测吞吐 36,697 行/秒（20000 条 / 545ms，设计指标 1 万/秒）。

> **脚本为什么是两张表**：`scripts` 按内容 hash 全局唯一（源码 + 元数据 + 首次出现的
> url/行号），`script_refs(inst, hash)` 表达「本次会话加载了哪些」。只留一张按 inst 存
> 源码的表，同一个 CDN 文件被 N 个会话加载就存 N 份；只留 hash 表又答不上「这次跑的时候
> 加载过哪些脚本」。
>
> 另一个坑：**内联 `<script>` 的 `url` 不是空串，而是它所在文档的 URL**。
> 拿 URL 判内联会把这些脚本全算成外链，判据是 `startLine > 0`（DevTools 同款）。
> 源码靠 `Debugger.getScriptSource` 单独取，**列表查询刻意不返回源码** ——
> 一页脚本的源码可能几十 MB，列表里带上它等于每翻一页把整个站点重传一遍。

## 6. 干预引擎（规则）

### 6.1 规则模型

```ts
interface Rule {
  id: string
  name: string
  enabled: boolean
  priority: number

  match: {
    urlPattern: string          // glob + 正则混合
    method?: string[]
    resourceType?: string[]
    statusCode?: number[]
    frameUrl?: string
    targetType?: string[]       // page / worker / service_worker
  }

  stage: 'request' | 'response'

  action:
    | { kind: 'block' }
    | { kind: 'redirect'; to: string }
    | { kind: 'delay'; ms: number }
    | { kind: 'rewriteHeaders'; set?: {}; remove?: string[] }
    | { kind: 'rewriteBody'; script: string }     // 沙箱内执行
    | { kind: 'fulfill'; status: number; headers?: {}; body: string }
    | { kind: 'mock'; fixture: string }
}
```

### 6.2 匹配性能

规则数上到几千条时，逐条正则会拖垮管道。做法：编译成按 host 分桶的前缀树 + 后缀/正则兜底，先按 host 快筛，再跑具体规则。目标：匹配耗时 < 50µs/请求。

**实测**：2000 条规则、5000 次匹配 = **4~6µs/次**（含动作执行），比目标低一个数量级。
分桶键就是 host，能抠出 host 的规则只进那个桶；桶内在编译期按优先级排好，匹配路径上零分配。

反推 `Fetch.enable` 的 pattern 同样按 host 收窄，但**端口要单独发一条**：实测
`*://host/*` 拦不到 `http://host:8080/x`，所以精确 host 会同时发 `*://host:*/*`。
能窄就窄是有收益的 —— 每条被拦的请求都多一次管道往返。

### 6.3 改写的两个坑

1. **`Fetch` 拦截是串行的** —— 所有命中请求都等你 `continue`。处理慢 → 页面整体变慢；处理中再发请求 → 容易死锁。必须异步 + 超时兜底（超时后自动 `continue`）。
2. ✅ **body 走 base64 过 IPC** —— 改 50MB 的响应会把页面卡住。**大 body 改写下沉到代理层**，
   CDP 只处理小 body。已落地（P5），分界与实测如下。

   **分界判据只能是 `content-length`**：CDP 那条路在 `declared > bodyMaxBytes`（256KB）时
   **根本不去取 body**（`body-capture.ts` 的 `tooLarge`）；代理按 `declared > sinkAboveBytes` 判。
   所以主进程把 `sinkAboveBytes` 固定下发成 `bodyMaxBytes` —— 两边**正好互补、绝不重叠**。
   重叠的后果是同一条 body 被改两遍（脚本不一定幂等），比漏改严重得多。

   **实测（`node work/sink-e2e.mjs`，6/6）**：同一份 `rewriteBody` 规则，同一个页面（含一个
   小 body 的 iframe），判据由**页面自己**报给 origin，不靠引擎自述 ——

   | | /big ≈ 400KB | /small 小 body | 应用侧计数 |
   | --- | --- | --- | --- |
   | 开代理 | REWRITTEN（代理改的） | REWRITTEN（CDP 改的） | `tooLarge=1`、`bodiesRewritten=5` |
   | 关代理 | **ORIGINAL**（CDP 拿不到这种 body） | REWRITTEN（CDP 自己就能改） | `tooLarge=1`、`bodiesRewritten=5` |

   规则这一侧的链路由 `src/main/proxy/rules.ts` 负责映射，只下发代理**能等价执行**的部分：

   - 只认 response 阶段的 `rewriteBody`（改头/拦截/延时 CDP 都做得了，发过去只会两边各执行一次）；
   - 匹配信号代理只有 `url` / `method` / `statusCode`，所以带 `resourceType` / `frameUrl` /
     `targetType` 约束的 body 规则**不下发**（拿不到信号就没法判，硬发等于丢掉用户写的约束），
     主进程日志会打出跳过条数与原因；
   - `urlPattern` 的 glob / `re:` 语义在主进程**一次性编译成正则**再下发（用的就是 matcher 那个
     `globToRegex`），代理只做 `test`；下发顺序 = 优先级（priority 降序、同号按列表顺序），
     代理「取第一条命中的」即等价于「每阶段只应用优先级最高的一条」；
   - body 脚本在代理进程里跑的是**同一份沙箱实现**（`proxy/rule-sandbox.mjs`；TS 侧
     `src/main/rules/sandbox.ts` 只做类型转出），超时/异常一律记 `ruleHits` 的 `applied:false` + 原因。

   **「只应用一次」是单独验过的**（`node work/double-apply-check.mjs`，2/2）：判据用**非幂等**脚本
   （`body.replace('MARK','MARK<!--DUP-->')`），默认配置与关掉 body 采集两种配置下，页面都正好数到
   1 个标记。用 split/join 那种幂等脚本是验不出重复应用的 —— 这正是「重叠」最危险的地方。

   已知边界（都是**约定**，不是漏做）：

   - 拿不到 `content-length` 的（chunked / 流式）两边都不改，如实记原因，绝不猜；
   - 二进制（`content-type` 非文本）和 CDP 那条路一样跳过（utf8 往返会把字节改坏）；
   - 流式的 `text/event-stream` 这类小 body：CDP 按 mime 跳过、代理按长度不下沉 →
     **两边都不改**。要覆盖它得让代理也判 mime，属于后续工作。

实现 P3 时又踩出来三个，记在这里免得重踩：

3. **响应阶段没有「只改响应头」的命令**：`Fetch.continueResponse` 声明了 `responseHeaders`，
   实测发过去页面读不到。改响应头只能把响应重发一次（`Fetch.fulfillRequest` + 用
   `getResponseBody` 拿 body）。拿到的是**已解码**字节，所以必须去掉 `content-length` /
   `content-encoding`，否则浏览器会拿 gzip 去解明文。拿不到 body 的（流式、超限、304）
   只能放弃这次头改写：少改一次，好过把响应毁掉。
4. **`Fetch.requestPaused` 里两种 headers 形态**：`request.headers` 是对象
   （`Network.Headers`），`responseHeaders` 是数组（`HeaderEntry[]`）。按数组去遍历对象会抛，
   而异常如果发生在计数器自增之后，统计里就会留下「生效过」的假账 —— 先算结果，再记账。
5. **注入脚本不能等导航**：`addScriptToEvaluateOnNewDocument` 必须在文档创建**之前**调用，
   而目标 URL 只有 `frameRequestedNavigation` 那一刻才知道，等 CDP 往返回来文档可能已经跑起来了。
   做法是挂载时不做 URL 过滤，把过滤编译成守卫写进脚本本体，在页面里拿 `location.href` 判断。
6. **响应规则要单独发一份 `Response` pattern**：`Fetch.enable` 的拦截范围原先只由**请求阶段**的
   规则反推，而关掉 body 采集（`MONITOR_CAPTURE_BODIES=0`）时那条覆盖全部类型的 `Response` pattern
   就不存在了 —— 于是「关掉 body 采集 + 只有响应规则」这个组合下，响应规则一条都不生效，
   页面上看不出异常、日志里也没有一个错。修法是 `engine.responsePatterns()`（同一套反推逻辑，
   `requestStage: 'Response'`）在 `enable()` 里一并下发；对照验收在 `npm run test:rules:e2e` 里
   （既验「关掉 body 采集后改写仍生效」，也验请求阶段的规则没被带坏）。

   注意只在 `!capturesBodies()` 时补发：采集开着时那条 `Response` pattern 已经把响应覆盖了，
   再发一遍会让同一条响应同时命中两个 Response pattern（实测 `body.paused` / `tooLarge` 各多一条）——
   修一个静默失效，别顺手引入一个重叠。

### 6.4 输入自动化

- 层次选择：`Input.dispatchMouseEvent`（`isTrusted=true`）> JS 派发（`isTrusted=false`，一眼假）
- **必须自己做拟人化**：CDP 的输入是「瞬间跳到目标点」，没有移动轨迹。真人是贝塞尔曲线 + 变速 + 停顿 + 微抖动。高级风控专门看这个。
- 坐标是视口坐标，需自行换算。

**P6 落地后的实测**：`buildTrajectory()` 用 mulberry32 按 seed 播种，同 seed + 同起点复现同一条曲线 —— 验收里重放两次，派发点数、规划路程（793.27px）、最大步长（25.58px）完全一致。

一次 `move → 900,600` 的页面侧实录：**68 个轨迹点 / 1167ms / 路程 658px（直线 611px，走的是弧）/ 最大步长 25px / 单步间隔 4.3~39.8ms / 2 次停顿**，`mousemove` 全部 `isTrusted=true`。行为检测器的判据是「单步 > 60px、间隔 CV < 0.12、步长 CV < 0.1、直线度 < 1.005、`isTrusted=false` 任一命中即判机器」，这条轨迹全过；验收脚本还会先把「一次跳到位的假轨迹」喂给检测器确认它真能判死，否则「通过」不算数。

三条从验收里逼出来的纪律：

1. **起手点不能是 (0,0)** —— 真鼠标不会停在窗口左上角。首次动作前光标未知，取视口正中（`Page.getLayoutMetrics`）。从角落起手会让弧线拐出窗口，而窗口外的坐标页面收不到 `mousemove`，录下来的轨迹就凭空多一个 282px 的「跳步」，一眼判死。
2. **控制点要夹进视口** —— 三次贝塞尔整条落在四个控制点的凸包里，控制点在窗口内，曲线就在窗口内。
3. **打字要有停顿** —— 等间距的按键节奏本身就是特征。词边界停一下，外加偶发 90~350ms 的「想下一个词」。
4. **窗口不能被节流** —— 被监控窗口被别的窗口盖住时，Chromium 按「不可见」节流渲染：鼠标事件回执被拖到 ~5s（8 点轨迹 40s、80 点轨迹 80s），`mousemove` 被按帧合并（轨迹里凭空多个 600px 跳步、滚轮总量少 12%）。这是启动参数问题，不是输入逻辑问题，所以修在 `launch.ts` 的三个抗节流开关上，而不是在轨迹里绕。
5. **动作完成 ≠ 页面已收到** —— 事件在浏览器里排队投递，`/input` 返回后页面还会继续收 ~150ms（实测 30 多个点）。所以动作收尾会等页面让两帧，验收脚本测量前也会等页面侧记录器安静下来。

### 8.4 三条实测发现（探针的判据就是照它们定的）

P6 做探针时踩出来三条与「常见说法」不一致的结论。每一条都直接决定探针怎么写，所以记在这里。

**1）「窗口从未真正显示」会让页面读到 `outerWidth/Height = 0`**

从 Electron 里 spawn 出来的内核，`Browser.getWindowBounds` 报 `normal`、尺寸也报 1280x900，
但窗口从没被真正 `ShowWindow` 过 —— 页面侧读到的是 `window.outerWidth/outerHeight = 0x0`、
`document.visibilityState = 'hidden'`。这正是「自动化标记」分组里最容易被判死的一条。

修法是 `controller.normalizeWindow()`：`Browser.getWindowForTarget` → `setWindowBounds { minimized }`
→ 等一会儿 → `setWindowBounds { normal, left, top, width, height }` → `Page.bringToFront`。
**必须走一趟 minimized → normal**：单独设 `normal` 不顶用，那一次状态跃迁才会强制触发真实的 `ShowWindow`。

而且这一趟在机器忙的时候会翻车：`minimize` 是异步落到窗口管理器上的，晚发的 `normal` 可能被它盖回去，
窗口就停在最小化。所以摆完要**回读校验并重试** —— `Browser.getWindowBounds` 的状态与尺寸要对，
Profile L 还能直接问页面一句（`JSON.stringify([outerWidth, outerHeight, visibilityState])`）再确认。

**2）`Navigator.prototype.webdriver` 是标准 IDL 属性，不是痕迹**

真实 Chrome 的原型上一直有这个访问器；`--disable-blink-features=AutomationControlled` 之后它**依然存在**，
只是取值变成 `false`。拿「描述符存在」当检测项会**误报**。探针因此把它降级成「记录」，参与判定的只有它的**值**。

**3）`Runtime.enable` 的痕迹，只有 console 调用的耗时测得出来**

网上流传的「console 参数序列化会泄漏访问器」那一类检测项，在本机 Chrome 153 上 A/B 实测**不成立**（同一会话内前后对照）：

| 检测项 | 无 Runtime | 有 Runtime | 可用？ |
| --- | --- | --- | --- |
| `console.debug` 每调用耗时 | 4.25~5µs | 24.75~53.75µs | ✅ **唯一可靠判据（约 7 倍）** |
| 参数 getter 是否被调用 | 0 | 0 | ❌ 没有差异 |
| Proxy `ownKeys` / `get` / `getOwnPropertyDescriptor` 触发次数 | 0 | 0 | ❌ |
| `toString` / `Symbol.toStringTag` 读取次数 | 0 / 1 | 0 / 1 | ❌ |
| `Error.prepareStackTrace` 调用次数 | 1 | 1 | ❌ |
| `console.debug.length` / 原生性 / 属性个数 | 0 / true / 25 | 0 / true / 25 | ❌ |

所以探针的判据是「每调用微秒数取三轮最小值」，用**绝对值**而不是和基线循环的比值 —— 基线循环会被 JIT
消掉（实测 0.05µs/次），除出来是个假数字。阈值取 15µs，落在两簇中间那道空档里（见 §3.4）。

**顺带两条同类记录：**

- **探针只能从顶层文档回报。** Profile H 的注入是「每个新文档都跑」，子框架也会执行一遍；子框架里
  `outerWidth` 恒为 0、视口是 iframe 自己的尺寸，那份报告只会污染结论（实测就是它让 H 的报告时不时读成
  `0x0`，而同一时刻主框架报的是 1280x900）。探针开头的 `if (window.top !== window) return` 是必须的。
- **不是所有 target 都有 `Fetch` 域。** 实测 `worker` 类型会回 `'Fetch.enable' wasn't found`。早先不分目标
  把失败记进全局状态，状态栏和探针面板就被它污染成「Fetch 域启用失败」，探针报告整块不出来。现在只有
  `page` / `iframe` 上的失败才算故障，其余降级成一行日志。

## 9. 技术选型

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 被监控浏览器 | 官方 Chromium（起手）→ 自编译 + patch（Profile H） | 保持零污染 |
| 浏览器驱动 | CDP over pipe | 无端口暴露 |
| Controller / UI | Electron + TypeScript + React | 生态最熟、CDP 库最全、开发效率最高 |
| 规则引擎 | TypeScript（起手）→ Rust（瓶颈时） | 先跑通再优化 |
| 采集与存储 | 独立 Node 22 存储进程 + `node:sqlite`（NDJSON RPC over stdio） | Electron 里加载原生 SQLite 会硬崩（实测）；重 IO 本就不该压在事件路径上 |
| 代理 | 先 mitmproxy（Python 脚本改写）→ 量产自研 | 快速验证优先 |
| 字节层 | 本地 CA + 代理 | 拿 DNS/TLS/帧，零编译成本 |

**原则：先用最便宜的东西验证，性能瓶颈出现再下沉。** 不要第一天就上 Rust 和自编译 Chromium。

## 11. 关键风险

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| Worker/SW 漏抓 | 以为监控成功实则漏一半 | P1 必须做多 target 覆盖，并与代理对照验收 |
| body 存储爆炸 | 磁盘被撑满 | 默认截断 + LRU + 只存 hash 的策略 |
| CDP 事件洪泛 | 卡死主进程 | 聚合 + 批量 + 环形缓冲，禁止同步 IO |
| Profile H 执行控制降级 | 无法断点调试 | 提前接受，用 Hook + 回传替代 |
| 自编译 Chromium 维护成本 | 项目性质变成维护内核分支 | **P4 之前先做最小 fork 验证**：只改 1–2 个文件，跑通「编译→分发→同步上游」全流程，量出真实成本再决定 |
| 三源关联歧义 | 数据串台 | 以 CDP 为主键，关联失败保留并存不合并 |

### 12.1 性能影响的量法（`npm run test:page-perf`）

三臂对照，同一台机器、同一个 `chrome.exe`、同一份负载页：

| 臂 | 监控 | 启动方式 |
| --- | --- | --- |
| `base` | 无 | 与容器**逐字相同**的启动参数，只去掉 `--remote-debugging-pipe` |
| `L` | 容器 · Profile L | `MONITOR_PROFILE=L` |
| `H` | 容器 · Profile H | `MONITOR_PROFILE=H` |

四条方法学上的硬要求（每一条都是被实测打出来才加的）：

- **数字由页面自己报。** 基线臂压根没有 CDP，只有「页面自量 + POST 回受控 origin」这条路，
  三臂量的才是同一件事。经 `Runtime.evaluate` 取数会把监控自己的开销算进去。
- **页面自己跑两轮，只认第二轮。** 第一轮吸掉的是一次性成本：新 profile 的浏览器启动
  （实测导航→脚本开始 270ms 上下）、V8 的 JIT 预热、连接池建立。这些跟监控无关，
  混进来会把倍数搅成 **0.5×**（监控开着反而「更快」）—— 这种数字比不测更糟。
- **两轮之间留 2s 静默。** 等容器把热身轮那 120 条请求的流水线（body 采集 → 关联 → 落库）
  排空。不等的话，计分轮的 cpu 段会和「容器消化上一轮」的排队撞在一起，纯 JS 计算
  实测被放大到 **5×** —— 量到的是排队，不是监控对页面的开销。
- **参照系是真实页面。** 服务端思考时间默认 15ms/请求：真实页面的耗时大头是网络与服务端，
  监控碰不到那一块。用 loopback 的 0 延迟当对照，等于假设页面全部耗时都贴着监控 ——
  那是上界，不是典型值（`node scripts/test-page-perf.mjs 3 0` 可复现）。

轮内交错（base → L → H）跑 3 轮取中位数；轮到某臂换臂时机器热漂移与后台抖动被抵消。
