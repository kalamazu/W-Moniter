# T-020：工作区检查点与冷恢复第一条链路

状态：已通过

认领：Codex（2026-09-24）

## 背景与目标

工作区已能隔离 Profile、SQLite、规则、布局、登录和插件证据，但尚无可验证的一致检查点与恢复。本任务建立“休眠工作区→原子快照→故障后冷恢复→重新对账”的第一条完整链路。

## 范围

- 要实现：仅在 suspended 且持有目录锁时创建版本化检查点；包含工作区索引、Profile、SQLite（含 WAL 一致备份）、规则、布局、下载元数据及 ContentRef 清单；校验 manifest/hash 后原子恢复同一 workspaceId，保留恢复前备份。
- 要修改的边界：WorkspaceService 状态机、checkpoint service/repository、文件备份与恢复、登录/插件对账、任务与 UI/HTTP/MCP 进度。
- 非目标：本卡不做跨机便携归档、跨 workspaceId 克隆或在线热回滚；不宣称 Cookie/Profile 恢复必然代表服务端登录仍有效。

## 依赖与风险

- 前置任务：T-000、T-002、T-005、T-011、T-013、T-014；ContentRef 完整性复用 T-008/T-012。
- 数据/兼容性/安全风险：恢复是破坏性动作；必须明确目标、预览差异、要求确认、写审计并先生成可回退备份。
- 需要 ADR 的取舍：快照一致性边界、ContentStore 共享对象的固定/引用计数、Profile 文件锁和恢复失败时的交换策略。

## 验收标准

- 用户或 Agent 流程：A/B 同时存在，休眠 A 并创建检查点；改动 A 的 Profile/规则/布局/资料后冷恢复，A 返回快照状态且 B 完全不变；恢复后登录置 stale并重新验证、插件重新观察。
- 自动化测试：覆盖一致 SQLite/WAL、文件更改/删除、大 Profile、缺失 ContentRef、manifest 篡改、磁盘不足、中途崩溃、重复恢复和打包版路径。
- 失败与边界行为：running/opening 工作区拒绝恢复；校验未通过时不替换现有数据；交换中断后能从恢复前备份重建确定状态，未知外部动作不重放。
