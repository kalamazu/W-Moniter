
**上一轮为什么判成硬墙**：只测了直连。直连时 `chrome-infra-packages.appspot.com` 被解析到
`198.27.124.186`（不是 Google，返回 301 的停车页），`Test-NetConnection` 连 Google 的 IP 也不通 ——
于是得出「整体不可达」。漏掉的是这台机器**本来就有一个可用的本地代理**
（`HKCU:\Software\Microsoft\Windows\CurrentVersion\Internet Settings` 里
`ProxyEnable=1`、`ProxyServer=127.0.0.1:7890`），而 `Invoke-WebRequest` / `git` / `cipd` 走的正是它。
教训：判「网络不可达」之前，先把 WinINET 代理设置读一遍。

### 0.1 P4 的判据（怎样才算做完）

P4 的产物只有一个：**一个打好补丁、能替换 `src/main/browser/locate.ts` 找到的那颗内核的二进制**。判据两步，缺一不可：

1. **工具链判据**：`gclient sync` 跑完 → `gn gen out/Release` 成功 → `autoninja -C out/Release chrome` 出产物。
2. **效果判据**：拿产物当内核重跑 `npm run test:probe`，H 面除了「CDP 痕迹零失败」，还要
   **二进制层三项也干净**（`隔离世界名注解` / `DevTools 工具脚本残留` / `Error.prepareStackTrace`）。

**P4 的设计决策点（未决，本轮没有替用户决定）**：H 现在按 §3.4 不开 `Runtime`/`Debugger`，
而二进制层泄漏的触发条件恰恰是这两个 domain —— 所以第 2 条判据现在**没有判别力**
（H 面三项天然干净，测不出差别）。要让它有意义，得先决定 H 是否要开 `Debugger`：
开 = 判据可测但隐蔽性假设要重估；不开 = 只能保留「官方 Chrome 的 H 面本来就干净」这条弱判据。

### 0.2 P7 的判据

P7（自建 content 壳 / mojo 无痕通道）在 §10 里是「P4 不够才启动」，所以它是**条件判据**：
P4 的产物在 `test:probe` 的二进制层仍有泄漏 → 才立项 P7，届时判据是「无痕通道下二进制层零泄漏」。
P4 没有产物之前，P7 既不必要也不可判 —— 这一点不变。

## 0.0 2026-09-19 实测进展（第 1 轮，CIPD 那条结论已被上面更正）

> ⚠️ 下面这段里的「CIPD 后端整体不可达」已被 §0 的复核证伪（是代理没配上，不是硬墙）。
> 其余实测记录（源码树 / Windows SDK / GN 的缺口）仍然有效，可直接复用。

已经做完的：

- **depot_tools 已装**：`F:\devtools\depot_tools`（`git clone --depth 1`，2.8s）。
- **预编译内核已装**：ungoogled-chromium **152.0.7977.82**（官方 release zip，188 MB，SHA256 与官方公布值逐字一致），
  解压在 `F:\devtools\ungoogled152\...`。它在本项目里**可以直接当内核用**：
  `CHROME_PATH=<...>\chrome.exe npm run test:probe` 得 **14/14**；`npm run verify` 得 **漏抓 0.00%（189/189）**。
  也就是说「换内核」这条链是通的，P4 只差「一个打好补丁的内核产物」。

撞上的硬墙（决定了自编译这条路本轮走不通）：

- **CIPD 后端整体不可达**。`chrome-infra-packages.appspot.com` 在本机被 DNS 污染
  （解析结果里混进 `199.59.148.206`），而且 Google 那几个真实 IP（`216.239.3x.10`）**TCP 443 全部连不上**。
  depot_tools 的 bootstrap（`bootstrap\win_tools.bat` 第 60 行 `cipd ensure`）正是从这儿拉它自带的 Python，
  于是卡死 20 分钟零字节。`gitiles` / `storage.googleapis.com` / `dl.google.com` / GitHub 都是通的，
  连依赖仓库一个个点过也都是通的：`chromium/src`、`skia`、`llvm-project`、`v8/v8` 全部 HTTP 200 —— **只有 CIPD 这一个后端不通**。
- 所以挡住 P4 的不是「Google 整体不可达」，而是**一条很窄的封锁**。只要能给 `*.appspot.com` 找到一条可用路由
  （用户侧代理 / 管理员改 hosts 指到可达 IP / 镜像的 pRPC 端点），`gclient sync` 就能跑；源码本身不必从别处搬。
  反过来，如果保持现状，把源码树完整拉下来也**编译不了**：`gclient runhooks` 要的依赖（GN、win_toolchain、第三方库）
  全在同一个 CIPD 后端上。
- 后果：`gclient sync` 拿不到依赖（GN、win_toolchain、测试 fixture 都走同一个 CIPD），
  所以走 depot_tools 的标准流程**编译不出 Chromium**，与磁盘和 VS 无关。

另外一个重要发现（会改变 P4 的判据）：

- 我给探针补了 3 条**二进制层**检测项（`隔离世界名注解` / `DevTools 工具脚本残留` / `Error.prepareStackTrace 回调`），
  然后拿官方 Chrome 与 ungoogled 各测一遍：**官方 Chrome 的 Profile H 三项全部干净**
  （`隔离世界名注解=无`、`工具脚本残留=无`、`prepareStackTrace=未被调用`，H 面 19 通过 / 0 失败）。
  原因是 H 的采集侧本来就没开 `Runtime`/`Debugger`，而这几条泄漏的触发条件恰恰是那两个 domain。
- 也就是说：**在 Profile H 的 domain 白名单下，我们现在测不出二进制层泄漏**。
  要把 P4 的判据定死，得再补一条「Debugger 路径」的检测（`Runtime.enable(false)` 本身就打不出来），
  这需要先决定 H 是否要开 `Debugger`（§3.4 现在写的是禁用它）。这是 P4 的**设计决策点**，不是纯环境问题。

## 2. 为什么没有「便宜版本」可做

- §3.4 把 Profile H 定义为「自编译 Chromium + 反检测补丁 + 指纹补丁」，§9 选型表也把被监控浏览器写成
  「官方 Chromium（起手）→ 自编译 + patch（Profile H）」。所谓「补丁」改的是**内核二进制**，不在本项目代码里，
  没有源码就无法产出。

- P7 更靠后：§10 写明 P7 只在「P4 不够」时才启动，P4 没有产出前无法判定其必要性。
- 本项目侧能做的那半（domain 白名单、只走 `Page.addScriptToEvaluateOnNewDocument`、
  探针自检「CDP 痕迹零失败」）已经做完并被 `npm run test:probe` 14/14 覆盖，**不需要自编译**。

## 3. 最小推进路径（拿到源码后按此执行）

§8 风险表里已定调：「P4 之前先做最小 fork 验证：只改 1–2 个文件，跑通『编译→分发→同步上游』全流程，
量出真实成本再决定」。落到操作是：

0. **先给 depot_tools 配代理 + 装 Windows SDK**（本轮新增的发现）：
   `set HTTP_PROXY=http://127.0.0.1:7890` / `set HTTPS_PROXY=...`（不配就对不上 CIPD），
   并补装 Windows SDK 10 的 `Include` / `Lib`（本机只有空的 `UnionMetadata`，见 §1）。
1. `fetch chromium` 拉一份源码树（depot_tools 已装好，见 §0）。
2. 只改 1–2 个文件（对照 `rebrowser-patches` 的泄漏清单挑最小改动），`gn gen` + `autoninja` 出一次编译。
3. 记录：首次全量编译耗时、增量编译耗时、产物体积、上游同步冲突量 —— 这四项就是「真实成本」。
4. 用产物替换 `src/main/browser/locate.ts` 找到的内核，重跑 `npm run test:probe`：
   H 面的判据要从「CDP 痕迹零失败」升级到「二进制层也检不出」。
5. 只有第 4 步不达标，才考虑 P7 的自建 content 壳。

## 4. 另一个未勾选项（不属于 P4/P7）

§8.1「JA3/JA4 与真实浏览器一致」当前是**有意的取舍**：开了代理后，被拦截 host 的出站 TLS 指纹是
抓包端（Node）的，不是 Chrome 的。也就是说开代理 = 用 TLS 指纹换 DNS/TLS 时序，所以代理默认关着
（`MONITOR_PROXY=1` 才开）。要对齐得上 uTLS 那一套，属于后续工作，不在 P4/P7 范围内。
